# مرور | Moroor V2 — سیستم مدیریت مرور و عملکرد مطالعه

داشبورد مطالعهٔ فارسی و راست‌چین با سبک بصری Glassmorphism، مرور فاصله‌دار، ثبت عملکرد روزانه، محاسبهٔ درصد آزمون با نمرهٔ منفی، تقویم شمسی تعاملی و ذخیره‌سازی ابری حساب‌محور.

## قابلیت‌ها

- ساخت پنج موعد مرور برای هر موضوع با فاصله‌های اولیهٔ ۱، ۳، ۷، ۳۰ و ۹۰ روز؛ امکان تنظیم فاصله‌ها از تنظیمات.
- ثبت تکمیل هر مرور، نمایش سررسیدهای امروز و عقب‌افتاده و فیلترهای ترکیبی.
- انتخاب تاریخ جلالی از تقویم پاپ‌آپ در فرم ثبت موضوع و فرم عملکرد؛ تاریخ داخلی به ISO ذخیره می‌شود.
- ثبت ساعت مطالعه، ساعت برنامه، تعداد تست، صحیح، غلط، نزده و تمرکز؛ اجازهٔ ثبت روز مطالعه با صفر تست نیز وجود دارد.
- فرمول درصد آزمون: `((صحیح × ۳) − غلط) ÷ (کل تست‌ها × ۳) × ۱۰۰`. پاسخ نزده امتیاز صفر دارد؛ مجموع صحیح، غلط و نزده باید با کل تست‌ها برابر باشد.
- نمایش شاخص‌ها و نمودارهای بازهٔ ۷ و ۳۰ روزه؛ هدف مطالعهٔ هفتگی اولیهٔ ۳۵ ساعت و ماهانهٔ ۱۵۰ ساعت قابل تغییرند.
- تم روشن و تاریک، طراحی Glass، چیدمان واکنش‌گرا، Command Palette، حرکت پنل‌های داشبورد و پشتیبانی از کاهش حرکت.
- پشتیبان‌گیری JSON و تبادل Excel در برگه‌های مرور، عملکرد و تنظیمات؛ هدف‌های مطالعه نیز در پشتیبان‌ها لحاظ شده‌اند.
- ساخت حساب/ورود اجباری پیش از نمایش داشبورد، ذخیرهٔ حساب‌محور در Supabase، ذخیرهٔ خودکار و دریافت تغییرات دستگاه‌های دیگر از Realtime.
- RLS جدول فضای ابری را به مالکیت همان کاربر محدود می‌کند.

## تاریخ و تقویم

تاریخ‌های برنامه در پایگاه داده به‌شکل ISO میلادی ذخیره می‌شوند؛ تقویم و نمایش کاربر شمسی است و با `jalaali-js` تبدیل می‌شود. برنامه هنگام آنلاین‌بودن تلاش می‌کند با هدر `Date` پاسخ سایت، تاریخ تهران را به‌دست آورد؛ اگر امکان‌پذیر نباشد از ساعت دستگاه استفاده می‌کند. تاریخ «امروز» در تقویم انتخابی با همین مبنای تاریخ برنامه هماهنگ است.

## شروع محلی و آزمون

نیازمند Node.js 20+ و npm:

```bash
npm install
npm test
npm run build
npm run preview
```

## راه‌اندازی Supabase

متغیرهای `VITE_SUPABASE_URL` و `VITE_SUPABASE_PUBLISHABLE_KEY` لازم‌اند. ابتدا سه migration موجود در `supabase/migrations/` را به ترتیب در Supabase SQL Editor اجرا کن و تنظیمات Auth و Repository variables را مطابق `CLOUD-SETUP.md` انجام بده. هرگز Secret یا `service_role` را در کد فرانت‌اند قرار نده.

هنگام ورود اول، اگر جدول ابری برای این حساب داده ندارد، برنامه از دادهٔ محلی موجود همان دستگاه برای مقداردهی اولیه استفاده می‌کند؛ اگر آخرین حساب استفاده‌شده متفاوت باشد، از انتقال ناخواستهٔ دادهٔ آن حساب به حساب جدید جلوگیری می‌شود. پیش از جایگزینی نسخه، همیشه یک فایل پشتیبان نگه دار.

## انتشار

Workflow موجود در `.github/workflows/deploy.yml` تست‌ها و Build را اجرا می‌کند، اما فقط Push روی `main` حق انتشار در GitHub Pages دارد. تغییرات را ابتدا در `v2-dev` آزمایش کن و فقط بعد از تأیید، به `main` منتقل کن.

## نکات همگام‌سازی

داده‌ها براساس حساب از یک ردیف JSON نسخه‌دار استفاده می‌کنند؛ تغییرات ذخیره‌شده به‌طور خودکار بین دستگاه‌های همان حساب جابه‌جا می‌شوند. ذخیره‌سازی با compare-and-swap و نسخهٔ `updated_at` انجام می‌شود؛ اگر دو دستگاه هم‌زمان ذخیره کنند، تغییرات رکوردهای مستقل ادغام و عملیات در صورت تعارض دوباره تلاش می‌شود. در تعارض ویرایش یک رکورد یکسان، تغییر محلیِ دستگاهی که در حال ذخیره است ترجیح داده می‌شود. این سازوکار جایگزین پشتیبان‌گیری نیست. در صورت شکست خواندن ابر، داشبورد برای جلوگیری از بازنویسی دادهٔ ابری نمایش داده نمی‌شود.
